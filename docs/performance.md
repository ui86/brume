# 实现说明与性能基准

## 代码结构

| 模块 | 职责 |
| --- | --- |
| `src/config.rs` | 解析命令行参数，校验认证配置及 IP/CIDR 白名单 |
| `src/dns.rs` | 使用配置的 DNS 服务器解析目标域名并缓存结果 |
| `src/protocol.rs` | 解析和编码 SOCKS5 请求、回复及 UDP 数据报 |
| `src/server.rs` | 监听 TCP/UDP、处理认证、转发流量并维护 UDP 关联 |
| `src/client.rs` | 提供 TCP CONNECT 和 UDP ASSOCIATE 客户端接口 |
| `src/client_dns.rs` | 读取客户端系统 DNS 与 hosts 配置，执行可取消的异步查询并复用缓存 |
| `src/dns_transport.rs` | 在各 DNS 上游内部完成截断后的 TCP 回退，保留多上游并行和原解析缓存 |
| `src/main.rs`、`src/lib.rs` | 启动服务及导出公共库模块 |

服务端在同一端口监听 IPv4 和 IPv6 的 TCP、UDP 流量。Tokio 运行时为每个 TCP 客户端创建异步任务，建立 CONNECT 后进行双向转发并支持半关闭。TCP 客户端最多同时处理 2048 个。每个方向的转发缓冲从 8 KiB 起步，满读时按需增长至 64 KiB；双向初始合计 16 KiB，最大 128 KiB；扩容后的方向连续 1 秒未读到数据时回收至 8 KiB，后续仍可按需增长。启用 `tcp_timeout` 时，任一方向成功转发数据都会刷新整个连接的空闲期限，写入阻塞也受该期限约束。

监听端口由单个实例使用，重复启动会返回绑定错误。TCP 接收连接失败后会进行可取消的短暂退避，避免临时资源耗尽导致全部连接退出或持续忙等；服务关闭时会停止并等待 TCP、UDP 报文和回复任务释放资源。本次安全与可用性修复、验证范围和后续性能优化见[审查记录](audit.md)。

UDP 接收循环最多允许 256 个并发数据包处理任务，所有关联合计最多保留 1024 个目标流，每个关联最多 128 个目标流；达到上限时，新连接或数据报会被拒绝或丢弃。同一目标的并发首包共用一次建流过程。每个目标流有独立的异步回复任务，套接字可读后从共享池借用约 64 KiB 接收缓冲，回复发送完成后归还；空闲流不独占缓冲。共享池最多保留 32 个缓冲，容量合计约 2 MiB。请求和回复都会刷新流的空闲期限，TCP 控制连接关闭后会立即取消回复任务。TCP 和 UDP 域名目标通过配置的 DNS 服务器解析，解析器复用服务端运行时，并按记录 TTL 缓存最多 8192 条响应；IP 目标直接使用地址。

UDP 数据报必须属于存活的 TCP 关联，来源 IP 与控制连接一致。客户端必须在关联请求中声明非零实际 UDP 端口，端口 `0` 的请求被拒绝；服务端按已声明的来源端点索引关联，不再允许同源 IP 首包抢占，也不兼容 NAT 改写 UDP 来源端口。UDP 域名目标在建流或发送失败时尝试已知备用地址；未收到回复的流到期后，下个数据报会从后续地址开始。白名单同时检查 TCP 和 UDP 来源地址，未配置时允许所有来源。加载白名单时按地址族将 IP、CIDR 转为数值范围，原地排序、合并重叠或相邻范围并缩容；每族不超过 4 个范围直接比较，其余二分查找。IPv4 映射 IPv6 和宽 IPv6 网段保留原匹配语义。

TCP 域名目标的 A、AAAA 查询独立进行，可用地址族一旦返回便开始连接，另一族仍可参与后续回退。DNS 和 TCP 建连共用 10 秒预算。UDP 同样先用已返回的可用地址建流，另一族在 10 秒 DNS 总预算内继续查询；失败流停止转发后仍持有流许可等待晚到地址，以便后续数据报回退。偏好地址按流代次更新，旧回复任务不会覆盖新流选择或重新插入已淘汰目标。两个地址族共享 Hickory 的 TTL 缓存。

客户端代理地址与 UDP 中继域名使用可取消的异步 DNS 网络查询，读取系统 DNS、搜索域和 hosts 配置，配置快照满 60 秒后按需刷新；系统配置读取通过每客户端最多一个阻塞任务完成，内容未变时保留工作槽的 TTL 缓存。每客户端最多 16 个解析工作槽和 32 个 DNS TCP 套接字，等待传输清理完成后才归还配额；按地址族优先复用工作槽及其 TTL 缓存，TCP 建连等待不占解析工作槽。代理域名逐族解析并开始连接，中继地址族允许短暂优先窗口后回退。系统 DNS 配置不可读时仍可命中 hosts，网络域名保留配置错误。该实现不执行 NSS、mDNS、LLMNR、NRPT、按接口拆分 DNS 或系统 DoH 策略，兼容边界见[使用说明](usage.md)。

客户端和服务端在同一个 DNS 上游内部处理 UDP 截断后的 TCP 重试，多上游仍并行查询；完整回复由原解析器继续执行 TTL 缓存。TCP 也返回截断时直接报错，避免循环重试。

## 验证

```bash
cargo fmt --all -- --check
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo test --locked --all-targets
```

本轮 81 项单元测试与 1 项命令行集成测试通过，覆盖 IPv4、IPv6 和域名报文、全部白名单前缀边界及逐项算法等价、认证、TCP 半关闭与缓冲增长、UDP 关联与流到期、渐进双栈 DNS、缓存、并发配额及查询取消。9 个普通 Bash 回归、真实描述符耗尽与恢复、独立网络命名空间防火墙已在临时 Linux 虚拟机验证；临时 systemd 服务的配置应用、重启失败及状态检查失败恢复也已通过 CI。发布工作流构建并用 UPX 压缩 Linux amd64 和 arm64 的静态链接程序。

## 运行基准

```bash
cargo bench --features performance-bench --bench benchmarks --locked
# 只运行指定分组，避免重复执行网络场景；可以同时指定多个分组
cargo bench --features performance-bench --bench benchmarks --locked -- whitelist
```

分组支持 `all`、`protocol`、`whitelist`、`udp`、`tcp`，省略时运行全部场景。以下数据于 2026-10-19 在 Windows、Rust 1.98.1 环境测得。基准程序每项先预热，再运行 5 轮，表格列出每次操作耗时的中位数。TCP 和 UDP 代理场景使用本机接收端或回显端，结果包含本机网络栈、线程调度和客户端处理开销。

| 场景 | 本机测量值 |
| --- | ---: |
| UDP 顺序代理往返，1024 字节 | 82.63 μs/包 |
| UDP 16 包流水线收发，1024 字节 | 21.17 μs/包 |
| TCP 连接目标并完成 SOCKS5 协商 | 3.19 ms/连接 |
| TCP 代理往返，1 KiB | 50.73 μs/次 |
| TCP 代理上传并等待确认，1 MiB | 0.76 ms/次 |

这些数字仅为当前本机参考值，不能据跨轮测量认定网络转发性能提升，也不代表公网延迟或 Linux 部署性能。并发连接数、目标数和报文速率变化时，耗时可能不同；实际部署应在目标机器按预期负载复测。

白名单另以相同输入、构建配置、迭代数和 5 轮中位数对照原逐项实现。小名单包含 1 个精确地址和 2 个网段；4096 个离散网段之间保留间隙，避免只测连续范围合并。

| 白名单场景 | 原逐项实现 | 范围实现 |
| --- | ---: | ---: |
| 小名单命中 | 6.58 ns | 4.79 ns |
| 小名单未命中 | 6.61 ns | 1.80 ns |
| 256 个连续 /16 未命中 | 236.36 ns | 1.56 ns |
| 4096 个离散 /24 末尾命中 | 3575.70 ns | 11.59 ns |
| 4096 个离散 /24 未命中 | 3666.33 ns | 11.84 ns |

当前 Windows x64 布局下，IPv4 范围为 8 字节，IPv6 范围为 32 字节。下表只统计 `Vec` 的容量负载，不含分配器开销；白名单结构头前后均为 48 字节，也不计入表内。

| 白名单输入 | 合并后范围数 | 原容量负载 | 新容量负载 |
| --- | --- | ---: | ---: |
| 3 条混合规则 | 2 个 IPv4、1 个 IPv6 | 140 B | 48 B |
| 256 个连续 /16 | 1 个 IPv4 | 4608 B | 8 B |
| 4096 个离散 /24 | 4096 个 IPv4 | 72 KiB | 32 KiB |

离散 IPv4 网段的容量负载减少 55.6%；IPv6 范围每项较大，实际占用仍取决于地址族、重复规则及可合并程度。TCP、UDP 的缓冲容量变化同样不能直接折算为进程常驻内存降幅。
