## 性能判断与后续优化

当前已经具备连接、报文任务和 UDP 流数量上限，UDP 关联使用端点索引，同一目标的并发首包共用建流过程，DNS 有 TTL 缓存。本轮主要改善资源回收与故障恢复，不据此声称吞吐量提升。

优先考虑以下后续工作：

1. DNS 的 A、AAAA 查询共同完成后才返回地址；其中一种查询持续无响应时，可用地址也要等待重试。应以本地 DNS 故障注入测量连接尾延迟，再评估逐步交付解析结果，避免削弱 IPv6 可用性和缓存语义。
2. TCP 双向缓冲合计约 128 KiB，1024 个 UDP 目标流的回复缓冲合计约 64 MiB，尚未计入套接字和其他对象。应在目标 Linux 机器测量并发数、吞吐量与常驻内存，再决定缓冲大小和容量参数。
3. 白名单仍为顺序查找。仓库已有 256 网段基准，小型名单的绝对耗时远低于代理往返；仅在大名单和高报文速率下证实为热点后，再引入前缀索引。

## 仍存在的边界

- 客户端 UDP 中继域名使用同步系统解析，尚未纳入总时限；中继地址与 TCP 控制连接地址族不同时，提前绑定的 UDP 套接字不能直接使用。需要同时调整解析与端口声明流程，并增加模拟代理测试。
- 外部客户端使用端口 `0` 建立 UDP 关联时，共享中继按同源 IP 的首个有效报文确定端口。同机或同 NAT 的其他发送者可能抢先占用该关联。当前客户端库声明实际端口；完整隔离需要每关联中继端口等协议架构调整。
- 安装脚本修改配置时仍直接停止服务。若 SSH 经由 Brume，连接中断可能使后续重启无法完成；候选配置的完整预校验与事务式替换也需后续实现。升级已使用独立安排的重启流程。
- 默认空白名单和空认证允许所有来源，用户名密码按 SOCKS5 标准明文传输；这些是现有配置与协议行为，部署方式见[使用说明](usage.md)。
