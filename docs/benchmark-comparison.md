# 核心性能优化基准对比

## 结论

本轮优化集中在服务器每个 UDP 数据包都会经过的路径。白名单检查、UDP 数据报解析和生产路径编码均已降为零分配；1024 字节 UDP 数据报的池化编码耗时降低约 93.4%，解析耗时降低约 75.0%。

按每秒 10 万个、负载 1024 字节的 UDP 数据包估算，优化前仅编码、解析和白名单检查就会产生约 128 MB/s 的临时堆内存，优化后这三部分不再产生每包堆分配。

## 核心结果

| 场景 | 优化前 | 优化后 | 耗时变化 | 分配变化 |
|---|---:|---:|---:|---:|
| 白名单精确匹配 | 38.98 ns，16 B，1 次 | 15.96 ns，0 B，0 次 | -59.1% | -100% |
| 单网段匹配 | 45.30 ns，16 B，1 次 | 9.07 ns，0 B，0 次 | -80.0% | -100% |
| 白名单未匹配 | 43.79 ns，16 B，1 次 | 9.40 ns，0 B，0 次 | -78.5% | -100% |
| UDP 编码，1024 字节 | 304.10 ns，1152 B，1 次 | 20.02 ns，0 B，0 次 | -93.4% | -100% |
| UDP 解析，1024 字节 | 54.24 ns，112 B，1 次 | 13.54 ns，0 B，0 次 | -75.0% | -100% |
| 请求解析，IPv4 | 75.93 ns，76 B，4 次 | 67.43 ns，80 B，3 次 | -11.2% | 次数 -25.0% |
| 请求解析，IPv6 | 82.62 ns，88 B，4 次 | 81.21 ns，92 B，3 次 | -1.7% | 次数 -25.0% |
| 请求解析，域名 | 110.20 ns，101 B，6 次 | 89.36 ns，88 B，4 次 | -18.9% | 次数 -33.3% |

UDP 编码的优化前结果来自兼容接口 `Datagram.Bytes`，优化后结果来自生产路径使用的池化 `Datagram.AppendTo`。兼容接口仍保留原有语义和分配行为。

IPv4 和 IPv6 请求解析把地址与端口合并到一块存储，因此分配次数减少一次，但内存分配尺寸等级使每次总字节数分别增加 4 B。该路径每个连接只执行一次，优先保留更少对象和统一存储结构。

## 网段规模

CIDR 白名单仍为线性扫描，但已完全消除分配：

| 未命中网段数 | 耗时 | 分配 |
|---:|---:|---:|
| 1 | 9.64 ns | 0 B，0 次 |
| 16 | 57.10 ns | 0 B，0 次 |
| 64 | 181.80 ns | 0 B，0 次 |
| 256 | 676.80 ns | 0 B，0 次 |

典型白名单规模下无需增加索引结构。如果实际配置长期超过数百个网段，可再考虑前缀树，但会增加实现复杂度和内存占用。

## 优化内容

### UDP 编码

- 新增向调用方缓冲区追加数据报头和完整数据报的接口。
- 服务器读取远端响应时预留最大 SOCKS5 UDP 头部空间，直接在同一缓冲区内完成封装。
- 客户端 UDP 写入使用池化缓冲区，不再为每个数据包分配完整切片。
- 缓冲池保存固定数组指针，避免切片放入接口时产生 24 B 装箱分配。

### UDP 解析与调度

- 新增返回结构体值的零拷贝解析入口，生产路径不再创建堆上的 `Datagram` 对象。
- 域名地址直接引用原始报文中包含长度字节的切片。
- UDP 工作队列改为传递任务值，避免每个任务单独分配指针对象。
- 兼容的指针返回解析函数和 `Handler.UDPHandle` 指针参数继续保留。
- 默认处理器在解析前进入值类型快速路径；自定义处理器继续走兼容指针路径。

### 白名单

- 精确地址由字符串映射改为 `netip.Addr` 映射。
- CIDR 由 `net.IPNet` 改为 `netip.Prefix`。
- 每包检查不再调用 `IP.String()`，IPv4 映射地址统一执行反映射。
- 并行精确匹配结果约为 2.47 ns/op，保持零分配。

### 请求解析

- 地址和端口改为一次连续分配。
- 域名长度字节直接写入最终存储，不再进行中间切片拼接。

### 内存上限

UDP 队列容量从 5000 调整为 1024，单个池化缓冲区从 65507 B 增加到 65769 B 以容纳最大 SOCKS5 头部。仅计算排队缓冲区时，理论上限由约 312.4 MiB 降至约 64.2 MiB，降低约 79.4%。队列满时仍沿用原有策略丢弃新数据包，避免无界内存增长。

## 范围说明

- `ParseBytesAddress` 已是约 2-3 ns 且零分配，没有继续修改。
- `ParseAddress` 和请求序列化主要用于连接建立，不位于 UDP 每包热路径。本轮保持其接口和实现，避免为了很小的收益增加写系统调用次数或缓冲池复杂度。
- `internal/core.Server` 的白名单字段类型已改为 `netip` 类型；仓库外部无法导入 `internal` 包，仓库内若存在直接构造这些字段的代码，需要同步使用新类型。
- 当前结果是微基准，不包含公网延迟、系统 UDP 缓冲区、网卡吞吐和实际客户端并发。生产环境容量评估仍应补充 Linux 目标机器上的端到端压测。
