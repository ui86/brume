# Rust 重构分析与验证范围

原项目由 Go 实现，主程序、SOCKS5 协议、TCP/UDP 转发和测试均位于 Go 包中。发布流程依赖 Go 构建，安装脚本依赖固定的 Linux 发行包命名。

本次重构将运行时迁移到 Rust：

| 模块 | Rust 实现 |
| --- | --- |
| 参数和白名单 | `src/config.rs`，严格校验参数及 IP/CIDR |
| SOCKS5 报文 | `src/protocol.rs`，解析请求、编码回复与 UDP 数据报 |
| 代理服务 | `src/server.rs`，TCP 并发转发、UDP 关联和目标流管理 |
| 程序入口 | `src/main.rs`，配置、信号处理与服务启动 |
| SOCKS5 客户端 | `src/client.rs`，TCP 连接、认证和 UDP 关联封装 |
| Rust 库入口 | `src/lib.rs`，导出客户端与协议模块 |
| 发布 | GitHub Actions 构建 Linux amd64/arm64 静态链接程序并保留安装包命名 |

## 行为差异

- UDP 数据报需要有效的 TCP UDP ASSOCIATE 关联。旧实现默认允许无关联 UDP 转发；在启用认证时这会绕过 TCP 认证。
- 无效的白名单条目现在会导致启动失败，避免拼写错误意外放宽访问范围。
- 用户名与密码必须同时指定；旧实现缺少其中一项时会退回无认证模式。
- 域名解析使用系统 DNS 配置，不再强制使用公共 DNS 服务器。
- Go 包中的客户端接口已迁移为 Rust 公共库。Rust API 与原 Go API 的命名不同，网络功能继续覆盖 TCP 与 UDP。

## 验证范围

Rust 测试覆盖协议 IPv4、IPv6、域名报文解析、UDP 数据报合法性、白名单、旧版命令行参数、认证、TCP 半关闭转发、UDP 关联限制、目标回复及客户端库端到端使用。CI 在 Linux 上执行格式检查、Clippy 和测试，Release 在 amd64 与 arm64 上分别构建。

## Rust 性能基准

执行命令：

```bash
cargo bench --features performance-bench --bench benchmarks --locked
```

测试环境：2026-10-09，Windows，Intel Core i5-12600KF，本地可用 4 个逻辑处理器，Rust 1.98.1。使用 Cargo 的优化基准配置，每项预热后运行 5 轮，表格取中位数。TCP 和 UDP 场景均使用本机回显或接收端；数值包含本机网络栈、线程调度和客户端处理开销。

| 场景 | 本机测量值 |
| --- | ---: |
| UDP IPv4 解析，1024 字节 | 6.43 ns/包 |
| UDP 域名解析，1024 字节 | 42.04 ns/包 |
| UDP IPv4 编码，1024 字节 | 42.77 ns/包 |
| 小白名单命中／未命中 | 7.12／7.19 ns/次 |
| 256 个网段白名单未命中 | 216.15 ns/次 |
| UDP 顺序代理往返，1024 字节 | 124.61 μs/包 |
| UDP 16 包批量收发，1024 字节 | 17.83 μs/包 |
| TCP 连接与 SOCKS5 协商 | 557.55 μs/连接 |
| TCP 代理往返，1 KiB | 71.79 μs/次 |
| TCP 代理上传，1 MiB | 1.09 ms/次 |

首轮优化前，同一基准的 UDP 顺序往返为 123.51 μs/包；优化后该指标没有可辨认的改善，不能据此声称端到端延迟提升。优化主要移除了服务端 UDP 收包与回包的逐包缓冲区分配，并将域名解析限制在新目标流建立时。TCP 监听改为阻塞接受并在关闭时唤醒，避免旧的 200 ms 轮询等待。实际收益仍需在目标 Linux 机器上用多连接、多目标与持续负载复测。

当前实现仍为每条 TCP 连接方向和每个 UDP 目标流使用线程；白名单网段及 UDP 关联查找也未建立索引。因此这些结果只是当前环境的基线，不能证明实现已达到最优。原 Go 微基准不能直接与 Rust 结果比较。
